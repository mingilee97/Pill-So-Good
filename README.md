# 💊 [AI13] 경구약제 이미지 객체 검출(Object Detection) 프로젝트

경구약제 이미지를 대상으로 **Object Detection 모델을 구축하고 Kaggle 대회 데이터에 대한 성능을 평가한 프로젝트**

Kaggle 원본 데이터와 AI Hub 경구약제 데이터를 활용해 팀원별로 End-to-End 방식의 모델을 구현했으며, 각 모델을 Kaggle Test 데이터에 제출하여 가장 높은 점수를 기록한 모델을 최종 모델로 선정함.

## 🎯 최종 모델 선정 방식

### 1. 개인별 End-to-End 모델 구현

각 팀원이 독립적으로 Object Detection 모델을 구현함.

```text
데이터셋 구성
      ↓
데이터 전처리
      ↓
Annotation 변환
      ↓
모델 학습
      ↓
Validation
      ↓
Test Image 추론
      ↓
Kaggle 제출
      ↓
성능 비교
```

팀원별로 서로 다른 모델 및 학습 방식을 적용하여 각각의 성능을 비교함.

### 2. Kaggle 제출 점수 비교

약 **900장 내외의 Test 이미지**에 대해 Object Detection을 수행하고 결과를 Kaggle에 제출함.

Validation 성능만으로 모델을 선정하지 않고, **실제 대회 Test 데이터에 대한 Kaggle 제출 점수**를 최종 평가 기준으로 사용함.

### 3. 최종 모델 선정 결과

팀원별 모델의 Kaggle 제출 점수를 비교한 결과,

> **김경원 모델을 최종 모델로 선정함.**

---

## 🔍 모델 선정 방식에 대한 이유

이번 대회의 Test 데이터에는 학습 데이터에 존재하는 Class뿐만 아니라 **기존 AI Hub 원본 데이터에 포함되지 않은 Class가 존재하는 상황**이 있었음.

따라서 단순히 Train / Validation 데이터에서 높은 성능을 기록하는 모델이 실제 대회 Test 데이터에서도 높은 성능을 보인다고 판단하기 어려웠음.

특히 이번 대회에서는 약 900장 내외의 Test 이미지를 대상으로 객체를 탐지한 후 결과를 제출하고 점수를 받는 방식이었기 때문에, **실제 Test 환경에서의 성능이 가장 중요한 평가 기준**이라고 판단함.

이에 따라 다음과 같은 방식으로 모델을 선정함.

```text
주어진 데이터셋
      ↓
다양한 전처리 및 학습 방법 적용
      ↓
팀원별 모델 구현
      ↓
모델 학습 및 추론
      ↓
Test 이미지 약 900장 추론
      ↓
Kaggle 제출
      ↓
점수 비교
      ↓
최고 점수 모델 선정
```

주어진 데이터셋만 활용해야 하는 제한적인 환경에서 여러 방법을 시도하고, **실제 Test 데이터에서 가장 높은 점수를 기록한 모델을 선택하는 것이 이번 대회의 취지에 가장 적합하다고 판단함.**

# 1. 데이터 EDA

### Kaggle 대회 데이터셋의 한계

**Class : 56종 · 사진은 221장**뿐.

## 추론

Kaggle 기본 제공 데이터셋만 활용할 경우 Class가 56종, 사진이 221장뿐이므로 **mAP만으로 모델 성능을 판단하기에는 한계가 있다고 판단함.**

또한 대회 평가 로직을 확인한 결과, **객체의 위치를 정확하게 예측하더라도 해당 Class가 학습 데이터에 포함되지 않은 경우 Class를 탐지하지 못해 0점으로 처리될 수 있다는 가설**을 세움.

따라서 **mAP뿐만 아니라 F2 Score 관점에서 Recall을 높이고, Test에 등장할 가능성이 있는 Class 종류를 최대한 확보하는 방향으로 전략을 수립함.**

**수집의 목표를 "데이터 양"이 아닌 "Class 종류 수"로 설정함.**
<br>
### 평가 지표

| 지표 | 설명 |
|---|---|
| **mAP@0.75:0.95** | IoU 0.75~0.95에서 **위치·분류 성능을 종합 평가** |
| **F2 Score** | Precision보다 **Recall(놓치지 않는 성능)**에 가중치를 둔 지표 |

> **mAP = 전체적인 검출 성능 / F2 = 놓치는 객체를 줄이는 성능**

### 수집 과정에서 지킨 제약

* **라벨 데이터를 먼저 확인한 후 필요한 원천 데이터만 다운로드함.**
* 원천 ZIP은 약 3GB 규모이므로, 7MB 수준의 라벨 데이터를 먼저 확인하여 **필요한 Class가 포함된 데이터만 선별함.**
* 조합 코드(`K-005000-...`)를 통해 라벨 데이터만으로 포함된 약품 종류를 사전에 확인함.

### 1-2. EDA 데이터 분석 결과

#### ① Class별 데이터 편중

118개 Class의 BBox 수가 크게 편중되어 있었다.

```text
BBox 수          Class 수
  0 ~  50개        11종
 50 ~ 100개        12종      ← 23종(약 20%)이 100개 이하
100 ~ 200개        37종
200 ~ 400개        51종
400개 이상          7종

중앙값 197개 · 최소 18개 · 최대 741개
```

→ 데이터가 부족한 Class의 성능 저하 가능성을 확인했다.

#### ② 장면 다양성 부족

```text
K-005000
데이터 7개 · BBox 21개

전체 중앙값
데이터 67개 · BBox 197개
```

→ `005000`은 데이터가 두 번째로 적은 Class였으며, 실제로 **`22074 → 005000` 오인식 사례**도 확인했다.

→ 단순히 데이터 양을 늘리는 것뿐만 아니라 **다양한 장면과 촬영 조건을 확보할 필요성**을 확인했다.

#### ③ 상자 형태의 다양성

```text
상자 종횡비 중앙값             0.99
1.3배 이상 길쭉/납작한 상자     42.8%
Class별 중앙 종횡비 범위       0.43 ~ 1.55
```

→ 실제 데이터에는 다양한 형태의 상자가 존재하므로, **다양한 상자 형태를 고려한 데이터 구성이 필요**했다.

### 전처리 파이프라인

#### ① 품질 검사

잘못된 BBox 및 라벨 데이터를 제거했다.

> 상자 누락 · 좌표 중복 · 이미지 범위 밖 · 빈 BBox
> → **296장 제외**

#### ② 데이터 누수 검사

Kaggle Test와 동일하거나 매우 유사한 이미지를 제거했다.

> **257쌍 일치 확인 → 211장 제거**

→ Test 데이터를 학습에 포함시키는 **데이터 누수 방지**

#### ③ 그룹 분할

유사한 장면이 Train/Validation에 함께 들어가지 않도록 **그룹 단위로 분할**했다.

> 조합 4,062개 → 그룹 2,895개
> **Train / Validation 간 중복 그룹 0개**

→ Validation 점수가 단순 암기가 아닌 **실제 일반화 성능을 반영하도록 구성**


### 전처리 파이프라인

**① 품질 검사** — label과 image가 매칭이 되지 않는 파일 제외

```
Bbox 누락 · 좌표 중복 · 사진 범위 밖 · 빈 bbox
→ v4 재구축에서 296장 제외
```

**② Data Leakage 전처리** — 캐글 test와 동일한 사진 제거

```python
# 사진을 64×64 흑백으로 줄이고, 평균·표준편차로 정규화한 뒤
v = (v - v.mean()) / (v.std() + 1e-8)      # 밝기·대비 차이를 지운다
sim = M_test @ M_hub.T / M_hub.shape[1]    # 전부 대 전부 코사인 유사도
leak = {hub[j] for _, j in np.argwhere(sim > 0.95)}
```

**v4 재구축에서 211장 제거** (캐글 test와 257쌍 일치).
데이터 누수를 제거하지 않으면 Test 데이터를 사실상 미리 학습한 것과 같아, **내부 평가 점수만 높아지고 실제 일반화 성능은 정확하게 평가할 수 없다.**

**③ 그룹 분할** — 같은 장면이 train/val에 걸치지 않게

같은 알약 조합을 **각도만 바꿔 3장**씩 촬영했다. 무작위로 데이터를 나누면 거의 동일한 사진이 train과 val에 동시에 포함되어, **검증 점수가 모델의 실제 성능이 아니라 학습한 장면에 대한 기억력을 반영할 수 있다.**

```text
비슷한 사진끼리 Union-Find로 묶어 그룹 통째로 배정
조합 4,062개  →  그룹 2,895개   (1,167곳을 이어붙임)

검증: 두 split에 걸친 그룹 0개
```

**④ 데이터  Crop** — 상자 + 여백 10%

```python
cx, cy = r.x + r.w/2, r.y + r.h/2          # 상자 중심
w, h = r.w * 1.10, r.h * 1.10              # 여백 10%
```

여백을 추가하는 이유는 **검출기가 예측한 상자가 정답 상자보다 조금 작더라도 알약의 일부가 잘리지 않도록 하기 위해서다.**
**학습과 추론 과정에 동일한 값을 적용**했다.


**⑤ 정규화** — ImageNet 통계 사용 (사전학습 가중치와 조건을 맞추기 위해)

### 전처리 방법 4종을 실험했다

| 방법                | 목적        |        결과(제출 점수) | 원인                                       |
| ----------------- | --------- | ----------: | ---------------------------------------- |
| **밝기 정규화**        | 조명 차이 완화  | **+0.0005** | 학습·추론에 동일하게 적용되어 조건이 일치함                 |
| **CLAHE (각인 강조)** | 각인 대비 향상  |     −0.0071 | 주변 밝기에 따라 보정 강도가 달라져 같은 알약도 이미지마다 다르게 보임 |
| **배경 제거**         | 배경 노이즈 제거 |     −0.0126 | 타원형 마스크가 캡슐·각진 알약의 **형태 정보를 손실시킴**       |
| **종횡비 보존**        | 이미지 왜곡 방지 |     −0.0137 | 예측 Class는 80종으로 증가했지만 전체 성능은 하락함         |

> **얻은 교훈:** 실패한 3가지 전처리 중 2가지는 **학습과 추론 과정의 조건이 일치하지 않은 것**이 주요 원인이었다.
>
> 특히 배경 제거는 학습 단계에서는 **정답 BBox**, 추론 단계에서는 **예측 BBox**를 기준으로 마스킹하여 입력 조건에 차이가 발생했다.
>
> 반면 성능이 향상된 **밝기 정규화는 학습과 추론에 동일한 방식으로 적용**되어 조건이 일치했다.

**실패한 전처리 모델도 폐기하지 않았다.**
최종적으로는 서로 다른 특성을 가진 모델을 활용하기 위해 **CLAHE 모델을 앙상블에 포함**했다. (6장 참조)

# 2. 모델 선정 및 설계

### 최종 아키텍처

```text
입력 이미지 (976×1280)
   │
   ▼
[1단계] YOLO11s
알약 위치 검출
   │
   ▼
검출된 BBox 기준 Crop
+ 주변 10% 여백
   │
   ▼
[2단계] ResNet18 × 9
118개 Class 분류
   │
   ▼
9개 모델의 확률 평균
→ 최종 예측
```

| 구성 요소 | 선택           | 규모                         |
| ----- | ------------ | -------------------------- |
| 검출기   | YOLO11s      | 9.4M · imgsz 416 · 1 Class |
| 분류기   | ResNet18 × 9 | 11.2M/모델 · 입력 224 또는 384   |
| 앙상블   | 확률 산술평균      | Class 확률만 평균               |

### 2-2. 모델 설계와 선택 이유

#### 결정 1 — 검출과 분류를 왜 분리했는가?

두 가지 구조를 비교했다.

```text
단일 모델
이미지 → YOLO → 위치 + 118개 Class 동시 예측

2단계 모델  ← 채택
이미지 → YOLO → 알약 위치 검출
             ↓
          Crop
             ↓
        ResNet18 → 118개 Class 분류
```

| 실험         | 조건             |                결과 |
| ---------- | -------------- | ----------------: |
| 단일 YOLO 1차 | 93종 · 4,522장   |           −0.0096 |
| 단일 YOLO 2차 | 118종 · 11,713장 | 0.60448 (−0.0163) |

단일 YOLO는 **데이터를 2.6배 늘려도 성능이 개선되지 않았다.**

→ **YOLO는 “어디에 있는가”, ResNet18은 “어떤 Class인가”로 역할을 분리**했다.
→ 검출과 분류를 각각의 모델이 집중하도록 **2단계 구조를 최종 채택**했다.


### 결정 2 — 왜 YOLO11s이고 왜 imgsz 416인가

검출 대상이 **단일 Class**이므로 큰 검출 모델이 필요하지 않았다.
검출 해상도는 실제 실험 결과를 기준으로 결정했다.

| 검출 해상도           |          점수 |    평균 BBox 크기 | 평균 확신도 |
| ---------------- | ----------: | ------------: | -----: |
| **416 (학습 해상도)** | **0.62316** | 257.6 × 286.5 |  0.940 |
| 640              |     0.57300 | 257.2 × 288.0 |  0.939 |
| 960              |     0.29187 | 215.4 × 243.9 |  0.762 |

→ **학습과 추론 해상도를 동일하게 416으로 유지하는 것이 가장 안정적이었다.**

특히 640은 평균 BBox 크기가 거의 동일했음에도 점수가 **0.050 하락**했다.
→ 평균적인 BBox 크기가 비슷하더라도 **개별 이미지에서의 검출 결과는 달라질 수 있음**을 확인했다.

### 결정 3 — 왜 ResNet18인가?

더 큰 모델과 다른 구조를 실제 학습하여 비교했다.

| 모델              |  파라미터 |  검증 균형 정확도 |  앙상블 기여 |
| --------------- | ----: | ---------: | ------: |
| **ResNet18**    | 11.2M | **0.9965** |      기준 |
| ResNet50        | 23.5M |     0.9963 | −0.0008 |
| EfficientNet-B0 |  4.0M |     0.9965 | −0.0042 |

→ **모델 크기를 키워도 성능 향상이 없었다.**

또한 세 모델의 **예측 일치율이 97.6~98.7%**로 매우 높았다.
→ 대부분 같은 예측을 하기 때문에 더 무거운 모델을 사용할 실익이 낮다고 판단했다.

### 결정 4 — 왜 분류기를 9개 사용하는가?

단일 모델의 성능이 **0.62464 수준에서 정체**된 이후, 추가 학습 없이 성능을 높이기 위해 **앙상블**을 적용했다.

```text id="e8khz5"
모델 A: 005000 → 22074   22074  0.70
모델 B: 005000 → 005000  005000  0.60
모델 C: 005000 → 005000  005000  0.50
────────────────────────────────
확률 평균                005000  0.37 > 22074 0.23
```

→ 단순 다수결이 아니라 **각 모델의 Class 확률을 평균**한다.
→ 일부 모델이 틀리더라도 다른 모델이 높은 확률로 올바른 Class를 예측하면 최종 결과에 반영할 수 있다.

**검출 BBox는 하나를 공유**하도록 설계했다.

```text id="z2o3py"
YOLO 검출
    │
    └── 동일한 BBox
         ├─ ResNet18 #1
         ├─ ResNet18 #2
         ├─ ...
         └─ ResNet18 #9
                 │
                 ▼
            확률 평균
```

검출까지 모델마다 다르게 수행하면 BBox 자체가 달라져 결과를 결합하기 어려웠다.
실제로 WBF 방식으로 검출 결과까지 결합했을 때는 **−0.0081의 성능 하락**이 발생했다.

→ 따라서 **검출은 하나의 YOLO11s가 담당하고, 동일한 알약 영역을 9개의 ResNet18이 각각 분류한 뒤 확률만 평균하는 구조**를 최종 채택했다.


# 결정 5 — 앙상블 9개는 정확히 무엇인가

여기서 **모델 하나 = 학습이 끝난 가중치 파일 하나**다.

`ResNet18`은 설계도(백본)이고, 실제 앙상블에 들어가는 것은 각각 학습된 `.pt` 파일이다.

```text
ResNet18
  └─ 설계도(백본)

runs_v3/clf_118.pt
runs_v4/clf384s_ep30.pt
...
  └─ 서로 다른 조건으로 학습한 가중치
```

따라서 이번 앙상블은 **같은 ResNet18을 9번 사용하는 것이 아니라, 서로 다른 학습 결과 9개를 결합하는 구조**다.

## 2. 무엇이 다른가

### 학습 데이터 — v3 vs v4

두 데이터셋 모두 118종이지만, v4에서 데이터가 부족했던 종류를 추가로 보강했다.

|    |      사진 |     상자 | 조합(장면) |
| -- | ------: | -----: | -----: |
| v3 |  8,898장 | 34,314 |  3,085 |
| v4 | 11,713장 | 44,818 |  4,062 |

대표적으로:

```text
016235 카듀엣정
v3   38개 → v4  440개

005000 비유피-4정
v3   21개 → v4  194개

학습 조각 100개 미만 종류
v3   23종 → v4    6종
```

즉, 종류 수는 같지만 **종류별로 학습한 장면의 수와 다양성이 다르다.**

### 입력 크기 — 224 vs 384

```text
224 × 224
→ 상대적으로 가볍고 빠름

384 × 384
→ 각인·표면 질감 등 세부 정보를 더 많이 유지
```

### 증강 — 약한 증강 vs 강한 증강

| 변형       |  224 |    384   |
| -------- | :--: | :------: |
| 회전       |   O  |     O    |
| 색상 변화    | ±25% | **±35%** |
| 블러       |   O  |     O    |
| 크롭·확대    |   —  |     O    |
| 기울이기·이동  |   —  |     O    |
| 일부 영역 제거 |   —  |     O    |

384 계열은 더 강한 증강을 사용해 특정 특징 하나에 과도하게 의존하지 않도록 했다.

### 전처리 — 원본 vs 밝기/대비 보정

```text
기본
└─ 원본 크롭

bright
└─ 전체 밝기 보정

clahe
└─ 국소 대비 강화
```

`bright`와 `clahe`는 단독 점수는 높지 않지만, **다른 모델과 다른 판단을 하기 때문에 앙상블에 포함했다.**

## 3. 4~7번은 왜 여러 개 넣었나?

`v4_384e10/20/30/40`은 같은 학습에서 저장한 서로 다른 epoch의 체크포인트다.

```text
v4 + 384 + 강한 증강
        │
        ├─ epoch 10
        ├─ epoch 20
        ├─ epoch 30
        └─ epoch 40
```

조건은 같지만 학습이 진행되면서 가중치와 예측이 달라진다. 따라서 서로 완전히 같은 모델은 아니며, **틀리는 위치도 조금씩 달라진다.**

## 5. 앙상블이 실제로 작동한 사례

전체 3,433개 상자 중 **9개 모델 가운데 5개 이하만 같은 답을 낸 경우가 47개** 있었다.

예를 들어:

```text
1069.png · 상자 194

모델          예측        확신도
────────────────────────────────
v3_224        33208        0.09
v3_384e30     6563         0.44   ←
v4_224        3544         0.09
v4_384e20     6563         0.96   ←
v4_384e30     10221        0.57
v4_384e40     6563         0.79   ←
v4_384e10     29345        0.37
bright        22347        0.11
clahe         22347        0.11
────────────────────────────────
최종          6563
```

`6563`은 3표뿐이지만 확신도가 `0.44 / 0.96 / 0.79`로 높았다.

반면 `22347`은 2표지만 둘 다 `0.11`이었다.

따라서 단순히 **표 수만 세는 다수결이 아니라 각 모델의 확률을 평균**해서 최종 답을 정한다.

## 결론

이번 9개 모델은 모두 ResNet18이지만,

```text
학습 데이터
입력 크기
증강 강도
전처리
epoch
    ↓
서로 다른 가중치
    ↓
서로 다른 예측
    ↓
확률 평균
    ↓
최종 분류
```

라는 구조다.

핵심은 **모델마다 잘하는 것과 틀리는 것이 조금씩 다르다는 점**이다.

따라서 단독 점수가 가장 높은 모델 하나를 고르는 대신, 서로 다른 모델의 예측을 합쳐 **개별 모델의 오판을 줄이는 것**이 이번 앙상블의 목적이다.

## 6. 9개 조합은 어떻게 결정했나

모델별 확률 행렬은 미리 파일로 저장해 두었다.

```text
모델별 확률 행렬 저장
        ↓
원하는 모델 조합 선택
        ↓
확률 평균
        ↓
제출 파일 생성
```

이렇게 해두면 모델을 추가하거나 빼는 데 다시 추론할 필요가 없다.
조합만 바꿔 바로 제출 파일을 만들 수 있기 때문에 여러 조합을 실제로 비교했다.

| 조합       |       점수 변화 | 결과                              |
| -------- | ----------: | ------------------------------- |
| 6개 → 9개  | **+0.0079** | `bright`·`clahe`·`v4_384e10` 추가 |
| 9개 → 11개 |     −0.0003 | 배경 제거·종횡비 보존 모델 추가              |
| 9개 → 10개 |     −0.0008 | ResNet50 추가                     |
| 9개 → 10개 |     −0.0042 | EfficientNet 추가                 |
| 9개 → 10개 |      0.0000 | 갈래 A 추가                         |

결과는 명확했다.

> **9개 조합에서 점수가 가장 높았고, 이후 다른 모델을 추가하면 성능이 유지되거나 떨어졌다.**

## 7. 성적이 낮은 모델도 왜 남겼나?

여기서 중요한 점은 **단독 점수와 앙상블 기여도가 다르다는 것**이다.

`clahe`는 단독 점수가 `0.61604`로 9개 중 가장 낮다.
하지만 앙상블에서 빼면 오히려 점수가 떨어진다.

반대로 `bgmask`는 단독 점수가 `0.61054`로 낮지만, `clahe`와 달리 추가했을 때 앙상블 성능이 `−0.0003` 떨어진다.

| 모델       |   단독 점수 | 앙상블               |
| -------- | ------: | ----------------- |
| `clahe`  | 0.61604 | **포함** — 제거하면 하락  |
| `bgmask` | 0.61054 | 제외 — 추가하면 −0.0003 |
| `lbox`   | 0.60702 | 제외                |

실제로 단독 점수만 보고 고른 조합과 비교하면 차이가 더 크다.

```text
성적이 좋은 3개만 사용       0.61925
실패작을 포함한 9개 사용     0.63420

차이                         +0.01495
```

즉, **단독 성적이 좋은 모델을 많이 넣는다고 앙상블 성능이 좋아지는 것은 아니다.**

`clahe`처럼 단독 성적은 낮더라도 다른 모델과 다른 판단을 하는 모델은 전체 조합에 도움이 될 수 있다.

> 앙상블에서 중요한 것은 **얼마나 잘 맞히는가**만이 아니라,
> **다른 모델과 얼마나 다른 방식으로 틀리는가**다.

이번 9개 조합은 이 기준으로 실제 제출 결과를 비교해 결정했다.

### Crop Size와 Epochs — 단독 변경은 오히려 손해였다

### Crop Size와 Augmentation — 따로 바꾸면 효과가 없었다

```text
384 Crop만 변경                  −0.0041
384 + 강한 Augmentation + 30ep   +0.0015  ← 단독 최고 기록
```

384로 Crop Size만 키웠을 때는 오히려 성능이 떨어졌다.

반면 **384 Crop + 강한 Augmentation + 30 Epochs**를 함께 적용했을 때 단독 최고 점수를 기록했다.

세 조건이 서로 보완되는 구조다.

* 강한 Augmentation → 더 다양한 형태의 입력을 학습
* 384 Crop → 크롭 과정에서 세부 정보가 덜 손실됨
* 30 Epochs → 늘어난 학습 난이도를 충분히 학습

즉, **384를 쓰는 것 자체보다 384 + 강한 증강 + 충분한 학습 시간을 함께 주는 것이 중요했다.**

### Epochs — 30에서 가장 높았다

100 Epochs 기준으로 학습하면서 중간 checkpoint를 저장해 비교했다.

| Epochs |          점수 |
| -----: | ----------: |
|     10 |     0.62114 |
| **30** | **0.62464** |
|     40 |     0.62103 |

**30 Epochs에서 가장 높았고, 40 Epochs에서는 다시 떨어졌다.**

학습을 더 오래 진행한다고 계속 성능이 좋아지는 것은 아니었다. 40 Epochs에서는 오히려 학습 데이터에 과도하게 맞춰지면서 성능이 떨어지는 모습을 보였다.

> **주의:** CosineAnnealing의 기준은 100 Epochs로 고정했다.
> 따라서 `EPOCHS=40`으로 설정해서 처음부터 40 Epochs만 학습한 것과, 100 Epochs 스케줄에서 40 Epochs 지점의 checkpoint를 사용하는 것은 학습률 변화가 다르다.
>
> 이번 실험에서는 **100 Epochs 스케줄을 유지한 채 중간 checkpoint를 저장해 비교**했다.


### Augmentation — 약한 증강과 강한 증강을 나눴다

224 계열은 기본적인 변형만 사용하고, 384 계열에는 크롭·Affine·Erasing 등을 추가했다.

|          | 224 계열 4개 | 384 계열 5개 |
| -------- | --------- | --------- |
| 180도 회전  | O         | O         |
| 색상 변화    | ±25%      | **±35%**  |
| Blur     | O         | O         |
| Crop·확대  | —         | **O**     |
| 기울이기·이동  | —         | **O**     |
| 일부 영역 제거 | —         | **O**     |

```python
# Strong Augmentation (384 계열)
T.RandomApply([T.RandomRotation((180,180))], p=0.5)          # 180도 회전
T.RandomResizedCrop(384, scale=(0.65,1.0), ratio=(0.85,1.18))  # 65~100% 크롭 후 확대
T.RandomAffine(degrees=10, translate=(0.05,0.05))           # 위치·각도 변화
T.ColorJitter(brightness=0.35, contrast=0.35,
              saturation=0.20, hue=0.03)                    # 색상 변화
T.RandomApply([T.GaussianBlur(3,(0.1,1.5))], p=0.3)         # 초점 흐림
T.RandomErasing(p=0.25, scale=(0.02,0.12))                  # 일부 영역 제거
```

여기서 `hue=0.03`은 다른 색상 변형보다 작게 설정했다.

알약은 **색 자체가 중요한 분류 단서**이기 때문에 hue까지 크게 흔들면 실제 종류의 색상 차이까지 훼손할 수 있다. 대신 밝기·대비·채도는 더 크게 변화시켜 촬영 환경의 차이에 대응하도록 했다.

`RandomErasing`(무작위 일부 제거)은 특정 특징 하나에 과도하게 의존하는 것을 막기 위해 사용했다.

예를 들어 각인이 항상 보이는 상태로만 학습하면 모델이 각인 하나에 지나치게 의존할 수 있다. 일부를 가린 이미지를 함께 학습시키면 각인이 보이지 않는 경우에도 **형태·색상·크기 등의 다른 특징을 함께 사용**하도록 유도할 수 있다.


### 튜닝하지 않은 항목과 이유

| 항목                                 | 상태              | 이유                                            |
| ---------------------------------- | --------------- | --------------------------------------------- |
| Loss Function                      | CrossEntropy 고정 | 학습 방식 변경 실험이 대부분 98% 일치에서 더 이상 개선되지 않음 (3-3절) |
| Label Smoothing                    | 0.05 고정         | 동일                                            |
| BatchNorm Statistics Re-estimation | 시도 후 폐기         | 성능 −0.0059 (3-3절)                             |

## 3-2. 성능을 적절한 평가 지표로 평가하였나요?

### Evaluation Metric — 대회 채점 방식을 그대로 구현했다

대회의 평가 지표는 **`mAP@0.75:0.95`**다.

```text
IoU Threshold
0.75   0.80   0.85   0.90   0.95
  │      │      │      │      │
  └──────┴──────┴──────┴──────┘
             평균
              ↓
              AP
              ↓
       전체 클래스 평균
              ↓
             mAP
```

IoU 0.5부터 평가하는 일반적인 설정과 달리 **0.75~0.95의 높은 IoU 구간만 사용**한다.

따라서 객체를 찾았다는 것만으로는 충분하지 않다.
예측한 Bounding Box가 정답 위치와 **상당히 정확하게 겹쳐야 높은 점수를 얻을 수 있다.**

```text
100px × 100px Bounding Box 기준

완벽한 예측
IoU 1.000
→ 0.75 ✓  0.85 ✓  0.95 ✓

5px 정도 어긋남
IoU 0.822
→ 0.75 ✓  0.85 ✗  0.95 ✗

10px 정도 어긋남
IoU 0.681
→ 0.75 ✗  0.85 ✗  0.95 ✗
```

즉, 이번 과제에서는 **분류 정확도뿐 아니라 Bounding Box를 얼마나 정확한 위치에 잡는지도 중요하다.**

그래서 로컬 평가에서도 대회의 `mAP@0.75:0.95` 계산 방식을 그대로 구현해 사용했다.

### 검출과 분류를 분리해 성능을 확인했다

내부 검증 데이터를 캐글과 같은 규칙으로 채점하고, **부품을 하나씩 정답으로 바꿔치기**했다.

| 시나리오 | mAP | 개선폭 | 해석 |
|---|---|---|---|
| ① 우리 파이프라인 그대로 | 0.9780 | — | 실제 실력 |
| ② 상자만 정답으로 | 0.9933 | +0.0153 | 검출을 완벽히 해도 이만큼뿐 |
| ③ 종류만 정답으로 | 0.9835 | +0.0055 | 분류를 완벽히 해도 이만큼뿐 |
| ④ 둘 다 정답 | 1.0000 | — | **채점기 검산 통과** |

**④를 넣은 이유**: 1.0이 안 나오면 채점기가 틀린 것이고, 그러면 ①②③ 숫자도 믿을 수 없다.
측정 도구를 먼저 검산하는 것이 측정의 첫 단계다.

### 보조 지표 — 균형 정확도

종류별 데이터가 불균형하므로 단순 정확도는 다수 종류에 끌려간다.
**종류별 정확도를 먼저 구하고 그 평균**을 취했다.

```python
per = collections.defaultdict(lambda: [0, 0])       # 종류별 [맞은 수, 전체]
for t, q in zip(정답, 예측):
    per[t][1] += 1
    per[t][0] += int(t == q)
bal = float(np.mean([a/b for a, b in per.values()]))  # 종류별 정확도의 평균
```

### 검증 설계의 한계를 확인하고 명시했다

**내부 지표는 끝까지 캐글을 예측하지 못했다.**

```
검증 균형 정확도   0.9965
검증 mAP          0.9780
캐글              0.6342
```

세 가지 검증 설계(그룹 분할, 홀드아웃 2회)를 시도했지만 **단 한 번도 캐글 순위를 맞히지 못했다.**
train과 val이 같은 촬영 환경에서 나왔기 때문이다. 그래서 **모든 판단을 실제 제출로만** 내렸다.

### 여기서 얻은 결론

실험을 많이 했지만, 모든 방법이 점수에 기여한 것은 아니다.

오히려 반복해서 확인된 것은 다음과 같다.

```text
큰 개선
→ 데이터 구성
→ 검출기 재학습
→ 서로 다른 모델의 앙상블

효과가 없거나 손해
→ 무작정 더 큰 Backbone
→ 복잡한 후처리
→ 과도한 전처리
→ 검증 점수만 보고 선택
```

결국 마지막 `0.63420`은 **하나의 결정적인 기법으로 만든 점수라기보다, 실제 제출 결과를 기준으로 효과가 없는 방법을 하나씩 제거하면서 남은 조합**에 가깝다.


### 실패 원인을 묶어보면

실패한 실험을 원인별로 다시 분류하면 몇 가지 패턴이 보인다.

| 원인               |    건수 | 해당 시도                        |
| ---------------- | ----: | ---------------------------- |
| **학습·추론 조건 불일치** | **4** | 배경 제거, CLAHE, 해상도 640·960    |
| 이미 성능 상한에 가까움    |     4 | Top-k, 장면 일관성, TTA, 사전확률 보정  |
| 모델 간 예측이 너무 비슷함  |     3 | ResNet50, EfficientNet, 갈래 A |
| 정보 손실            |     2 | 배경 제거, 종횡비 보존                |
| 촬영 환경이 다름        |     1 | 단일 알약 데이터                    |

몇 가지 실험은 이름만 보면 다른 방법처럼 보이지만, 실제로는 **학습과 추론의 조건이 달라지는 순간 성능이 크게 떨어진다**는 공통점이 있었다.

---

### 왜 더 이상 오르지 않는지 확인했다

실패 원인을 단순히 추측하지 않고, 몇 가지 진단 실험을 추가했다.

#### ① Top-k 실험 — 후보를 늘려도 해결되지 않았다

각 상자에 가장 가능성이 높은 종류를 여러 개 넣어보았다.

| Top-k |  커버한 종류 |
| ----: | ------: |
|     1 |      75 |
|     3 |     115 |
| **5** | **118** |

Top-5에서는 **118종 전체가 이미 후보 안에 들어왔다.**

그런데 점수는 `+0.0001`밖에 오르지 않았다.

즉, 문제가 **“맞는 종류를 후보로 제시하지 못하는 것”은 아니었다.**

> 맞는 답을 후보로는 가지고 있지만, **그중 어떤 답을 선택하느냐에서 틀리고 있었다.**

---

#### ② Feature Vector 분석 — 어려운 종류를 찾았다

분류층을 제외하고 ResNet18의 **512차원 Feature Vector**를 추출해 테스트 조각과 학습 데이터의 유사도를 비교했다.

```text id="0kn1bc"
전체 test 조각
│
├─ 학습 데이터와 유사한 정도 (median)   0.987
│
└─ 1-NN과 앙상블의 예측 비교
      └─ 같은 답                       98.1%
```

대부분의 샘플에서는 학습 데이터와 가까웠다.

하지만 유사도가 낮은 샘플만 따로 보면 차이가 컸다.

```text id="3p4h0j"
가장 안 닮은 10% (344개)   → NN 불일치 14.8%
나머지 90%                → NN 불일치  0.4%

                              약 37배 차이
```

이 결과를 통해 단순히 **“모델이 전체적으로 부족하다”**가 아니라, 특정 종류나 샘플에서 문제가 집중되어 있다는 것을 확인할 수 있었다.

그중 특히 의심스러웠던 종류는 다음과 같다.

| 종류                 | 예측 수 | 평균 유사도 |  NN 불일치 |
| ------------------ | ---: | -----: | ------: |
| `22347` 자누비아정 50mg |   80 |  0.959 | **21%** |
| `6563` 조인스정 200mg  |   43 |  0.941 | **19%** |
| `27926` 울트라셋이알서방정  |   25 |  0.981 |     12% |
| `3544` 무코스타정       |  175 |  0.916 |      9% |

특히 `22347`, `6563`은 학습 데이터와의 유사도가 상대적으로 낮고, **가까운 학습 샘플이 제시하는 답과 앙상블의 답이 자주 달랐다.**

이 단계에서 처음으로 **어떤 종류가 실제 성능을 방해하고 있는지 구체적인 후보를 좁힐 수 있었다.**

### ③ 앙상블 조합 실험 — 모델을 더 넣는다고 좋아지지는 않았다

모델별 확률 행렬을 미리 저장해 두고, 추론 없이 조합만 바꿔가며 비교했다.

| 구성                |  모델 수 |          점수 |
| ----------------- | ----: | ----------: |
| 성적 좋은 3개만         |     3 |     0.61925 |
| 기본 조합             |     6 |     0.62632 |
| **실패작 포함**        | **9** | **0.63420** |
| 11개               |    11 |     0.63392 |
| 9개 + ResNet50     |    10 |     0.63345 |
| 9개 + EfficientNet |    10 |     0.63001 |

단독 점수가 좋은 모델만 골랐을 때보다, 단독 성적이 낮은 `bright`·`clahe` 등을 포함한 9개 조합의 점수가 더 높았다.

> **앙상블에서는 단독 성능보다 예측의 다양성이 중요하다.**
> 개별 성능이 낮더라도 다른 모델과 다른 곳에서 틀리면 전체 성능에 기여할 수 있다.

---

## 마지막 실험 — 문제는 모델이 아니라 입력에 있을 수 있다

9개 모델을 비교하면서 한 가지 한계를 의심했다.

**모든 모델이 결국 같은 1단계 검출기가 만든 Bounding Box를 보고 있다.**

그렇다면 분류 모델을 아무리 바꿔도, 검출기가 놓친 정보나 잘못 잘라낸 영역에서는 같은 오류가 반복될 수 있다.

이를 확인하기 위해 **상자부터 다르게 만드는 별도 파이프라인(갈래 A)**을 118종으로 다시 학습해 앙상블에 추가했다.

```text id="b19h5g"
갈래 A vs 기존 최고 조합
→ 예측 일치율 99.9%

기존 2단계 모델끼리
→ 예측 일치율 97 ~ 99%

갈래 A 추가 후
→ 최종 결과가 달라진 상자 0개
```

갈래 A는 데이터 구성부터 전처리, 증강, Crop, Backbone, Pipeline까지 기존 방식과 상당히 다르게 만들었지만 **최종 예측은 기존 앙상블과 사실상 같았다.**

> **모델을 크게 바꿔도 같은 상자에서 같은 답을 낸다면, 문제는 모델 구조보다 그 상자 자체에 있을 가능성이 높다.**
>
> 결국 이번 실험에서 확인한 한계는 **새로운 모델을 더 만드는 것보다, 모델이 학습할 데이터와 입력을 어떻게 구성하느냐가 더 중요하다는 것**이었다.

## 재실행 비용을 줄이는 구조

### ① Checkpoint / Resume

몇 시간씩 걸리는 학습이 중단되어도 이어서 실행할 수 있도록 매 Epoch마다 모델뿐 아니라 Optimizer와 Scheduler 상태까지 저장했다.

```python
# 매 Epoch마다 Checkpoint 저장
torch.save({
    "ep": ep,
    "model": m.state_dict(),
    "opt": opt.state_dict(),  # SGD momentum 상태
    "sch": sch.state_dict(),  # Learning Rate Scheduler 상태
}, CK)

# Checkpoint가 있으면 자동 Resume
if os.path.exists(CK):
    ck = torch.load(CK)
    m.load_state_dict(ck["model"])
    opt.load_state_dict(ck["opt"])
    sch.load_state_dict(ck["sch"])
    START = ck["ep"] + 1
```

모델 가중치만 복원하면 SGD의 `momentum`과 Learning Rate Scheduler의 진행 상태가 사라진다. 따라서 **학습을 중단한 지점부터 동일한 조건으로 이어가려면 세 상태를 함께 저장해야 한다.**

### ② Intermediate Result Caching

앙상블 실험에서는 매번 모델을 다시 추론하지 않도록 **Probability Matrix와 Detection Box를 미리 저장**했다.

```text id="m2eh4w"

→ 13개 모델의 Probability Matrix

→ Detection 결과

        ↓
Submission 생성까지 몇 초
```

덕분에 수십 개의 조합을 실제로 비교할 때도 추론 시간을 다시 들이지 않았다.

### ③ 디스크 사용량 절감

| 학습 데이터와 유사한 약 |   정확도 **약 99%** | 등록된 약은 높은 신뢰도로 인식 가능 |
| 약품 커버리지       | 약 **78종 중 50종** | 미등록·낯선 약에서 인식 한계 존재  |

### 핵심 리스크 — "모르는 약을 아는 약으로 판단"

모델의 평균 확신도는 **약 0.94**지만 실제 인식 정확도와 차이가 있다.

> **의료 서비스에서는 틀린 답을 확신해서 제공하는 것이 단순한 인식 실패보다 위험하다.**

따라서 현재 모델은 **완전 자동 판독보다는 사용자 확인을 포함한 보조 기능**으로 활용하는 것이 적절하다.

### 서비스 적용 방향

| 적용 단계       | 제안                                 |
| ----------- | ---------------------------------- |
| **현재 단계**   | 자동 확정 대신 **Top-3~5 후보 + 사용자 확인**   |
| **불확실한 결과** | 앙상블 불일치 구간을 **"확인 필요"**로 처리        |
| **낯선 약품**   | 학습 데이터와의 특징 거리 기반으로 **"인식 불가"** 판별 |
| **의료 의사결정** | 복약·처방 판단을 모델 결과만으로 수행하지 않음         |

### 가장 중요한 비즈니스 시사점

실험 결과, 모델 구조를 변경하는 것보다 **인식 가능한 약품의 종류를 확대하는 것이 훨씬 큰 성능 향상**을 가져왔다.

| 투자 방향               |     투입 |        성능 변화 |
| ------------------- | -----: | -----------: |
| 모델 구조·전처리·증강 등 개선   | 약 40시간 | **+0.01 수준** |
| 약품 종류 및 데이터 커버리지 확대 |  약 8시간 |   **+0.163** |

14개 이상의 모델과 다양한 전처리·증강·크롭·백본을 비교했지만 성능 차이는 제한적이었다.

> **결론: 이 프로젝트에서 성능을 결정하는 핵심 병목은 모델 구조보다 데이터 커버리지였다.**

현재 약 **118종**을 대상으로 하지만 실제 국내 유통 경구약은 훨씬 많기 때문에, 서비스 확장을 위해서는 **신규 약품 데이터를 지속적으로 수집·검증·학습하는 데이터 파이프라인 구축**이 우선되어야 한다.

### 최종 인사이트

**모델을 더 복잡하게 만드는 것보다 `인식 가능한 약품의 범위`를 넓히는 것이 서비스 가치에 더 직접적으로 기여한다.**

따라서 Health Eat의 다음 단계는
**① 약품 DB 확대 → ② 낯선 약품 감지 → ③ 사용자 확인 기반 UX → ④ 지속적인 데이터 수집·재학습**의 순서로 고도화하는 것이 적절하다.

### 목표 대비 달성도

| 목표            |    달성도    | 근거                            |
| ------------- | :-------: | ----------------------------- |
| 사진에서 알약 위치 검출 |   **충족**  | 재현율 **99.5%**, 사진당 평균 4.1개 검출 |
| 알약 종류 식별      | **부분 충족** | 학습된 약품은 높은 정확도, 미학습 약품은 오인식   |
| Kaggle 점수 향상  |   **충족**  | **0.42532 → 0.63420 (+49%)**  |
| 재현 가능한 파이프라인  |   **충족**  | 실행 7.4분 및 결과 파일 일치 검증 완료      |

### 문제 정의를 재정의했다

초기에는 **"분류 정확도를 높이는 것"**을 핵심 문제로 정의했다.
하지만 자체 채점기를 통해 원인을 분해한 결과, 실제 병목은 달랐다.

```text
상자만 정답으로 교체   → +0.0153
종류만 정답으로 교체   → +0.0055
```

즉, **검출과 분류 자체의 개선 여지는 제한적**이었고, 가장 큰 문제는 **모델이 학습하지 못한 약품을 처리할 수 없다는 것**이었다.

### 문제 정의 변경의 효과

이에 따라 목표를 **모델 정확도 개선 → 약품 커버리지 확대**로 전환했다.

```text
추정 성능 상한
= 50종 × 0.98 ÷ 78종
≈ 0.628

실제 최종 점수
= 0.63420
```

추정치와 실제 점수의 차이는 약 **0.006**에 불과했다.

> **결론:** 최종 성능의 주요 한계는 모델 구조나 검출 성능보다 **인식 가능한 약품의 범위(커버리지)**에 있었다.
> 따라서 프로젝트는 초기의 단순한 "정확도 향상" 목표에서 **"실제 서비스에서 처리 가능한 약품 범위 확대"**라는 방향으로 문제를 재정의했고, 실험 결과를 통해 그 판단을 검증했다.
